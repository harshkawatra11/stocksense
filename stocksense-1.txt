● Good call — but there's a hard constraint: DuckDB only allows one process to 
  hold the database file open at a time (we saw this earlier — the read-only
  query failed while the write job held the lock). So two processes can't write
  to the same DB concurrently; the second one would just fail to even open the
  connection.

  What can run in parallel safely: the network-fetch-to-disk-cache step doesn't
  touch the database at all (_cached_or_fetch just writes zip/csv files). So I
  can kick off a prefetch-only process for 2010–2014 right now that downloads to
  the on-disk cache concurrently with the current job — no DB conflict. Then
  once the 2015–2026 job finishes, running backfill-nse-archive --start 
  2010-01-01 --end 2014-12-31 will replay almost instantly from that warm cache
  instead of waiting on fresh downloads.

  One tradeoff: both processes hitting NSE's servers at once roughly doubles the
  request rate — should still be fine at ~1 req/sec each, but worth knowing.
