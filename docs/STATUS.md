## The Foreman: self-building harness (2026-08-16, same day, second build phase)

The plan pivoted from "build the remaining phases by hand" to "build a harness that builds them" — see `C:\Users\harsh\.claude\plans\indexed-discovering-summit.md`. All prior phases (data spine, skills, RAG, optimizer, loops, intraday, the Electron desktop app) become the Foreman's **backlog** rather than a manual sequence.

**Built and tested (188 tests passing, up from 103):**

- **CI** — `.github/workflows/verify.yml`, the independent referee. Runs the full suite plus the leakage and determinism suites as separately-named steps on every push/PR, and checks `.env` never entered history. The Foreman may only self-merge on a **green remote** run (via `gh run list`), never its own local test pass.
- **`foreman/policy.py`** — the single most important file in this build. A literal allowlist of protected paths (`evaluation/gate.py`, `walkforward.py`, `cost_model.py`, the leakage/determinism/gate tests, any preregistration doc, and the policy file and CI workflow themselves). Touching one is a routing decision — the goal branches to a human-reviewed PR and halts, never a silent write.
- **`foreman/tools/`** — a closed, typed tool registry (`base.py`) so a hallucinated tool name fails fast in the executor. `code.py` (read/search/write/test/lint) and `git_tools.py` (branch/commit/push/PR/CI-check) are the first two groups; `write_patch` is the sole write path and checks `policy` before touching disk.
- **`foreman/planner.py`** — Claude decomposes a goal into a plan, validated against the tool registry and converted into a `harness.Graph` (reusing the Phase 0 graph/runner rather than a second execution engine).
- **`foreman/executor.py`** — runs the plan, routes on the verifier's verdict: protected path → PR always; unprotected + fully green including remote CI → auto-merge; anything else → `blocked` with a written reason, never retried past `max_attempts`.
- **`foreman/verifier.py`** — the sequential gate chain (protected-paths → local tests → leakage → determinism → remote CI → pre-registered gate for research goals), ordered so expensive remote checks never run on a result that already failed something cheap.
- **`foreman/adversary.py`** — a red-team pass that tries to falsify a result before it's accepted: assertionless tests, swallowed exceptions, tautological assertions, and (for research goals) seed-sensitivity of the headline number. A blocking finding downgrades an otherwise-merged result.
- **`foreman/assess.py`** — reads real signals (test count, which backlog markers exist, recent goal outcomes, protected-violation count) and asks Claude to propose ranked goals with reasons — the self-assessment that makes this "build itself" rather than execute a fixed list.
- **`foreman/budget.py`** — daily invocation cap + a cooperative kill switch. Cadence is on-demand per the user's choice; scheduling is future work, not built now.
- CLI: `stocksense foreman run "<goal>"`, `foreman assess`, `foreman status`, `foreman ledger`.

**Bugs found and fixed by this build's own tests, all real, none cosmetic:**
1. `policy._normalize` used `str.lstrip("./")`, which strips arbitrary leading `.`/`/` *characters*, not a literal prefix — silently ate the dot off `.github/workflows/...` and made the CI-workflow protection pattern never match. The one test written specifically to guard the CI workflow's own protection caught it before anything shipped.
2. `foreman/tools/__init__.py` only re-exported `base`, so importing `stocksense.foreman.tools` without also importing `.code`/`.git_tools` left the registry empty — a planner-only test file failed six ways until the package `__init__` was made to import every tool module explicitly for its registration side effects.
3. `adversary.check_assertionless_tests` checked for the literal substring `"pytest.raises"` inside `ast.dump()` output, which renders attribute access as nested `Attribute(...)` nodes, not dotted text — so it never matched and every legitimate `pytest.raises`-based test was misflagged as assertionless. Fixed with `ast.unparse` to get real source text. Notable because this bug was *in the module whose entire purpose is catching bugs like this*.

**Not yet built:** the loop scheduler (on-demand only for now), a real invocation of `foreman run` against a live goal (only exercised in this session via mocked git/network calls — no real branch, commit, push, or PR has been created yet), and the backlog items themselves (Electron app, reconcile loop, data spine, skills, RAG, optimizer, intraday track) — those are queued as the Foreman's first real work, not done.

## Phase E4: intraday track — GATE FAIL, retired (2026-08-21/22)

The dedicated intraday research track `phase0_verdict.md` opened (Upstox minute-bar spine, MIS-cost model, same-day label) was built end-to-end and run for real. `research/preregistration_intraday.md` fixed `stop_pct=1.0%`, `target_pct=1.5%`, `max_holding_minutes=60`, `top_n=10`, `exposure_inr=₹75,000` — every parameter grounded in the user's own closed-position statement or reused unchanged from the daily pipeline — **before** the sweep ran, and named in advance what a FAIL would mean: report and stop, not retune.

**Result (`research/verdict_intraday.md`): GATE FAIL.** 15 folds, ~400,000 simulated trades over the real 91.2M-bar spine, **0/15 folds net-positive**, mean net alpha −0.117%/trade. The decisive detail: `research/intraday_fold_results.csv`'s `gross_expectancy` column is **negative in every fold, before a single rupee of cost**. A ranker with no gross edge cannot be rescued by cheaper execution, wider stops, or a different `top_n` — which is exactly why the pre-registration forbids adjusting those after seeing this result.

**The user's own real account independently confirms it, on live capital rather than backtest.** 441 real intraday round trips, 2026-08-04 → 08-17 (`positions` table): gross **+₹2,492**, charges **−₹3,785**, net **−₹1,293**. The selection itself was gross-positive; ~44 round trips/day on ~₹8,000 tickets (charges = 152% of gross profit) is what turned it negative. Same finding, arrived at by two independent methods.

**Two real performance bugs were found and fixed while running the sweep** (not research findings, engineering ones — see the commit that shipped them): a single-shot 91.2M-row load that pushed a 16GB machine into heavy paging, and an O(entries × fold_data_size) label-lookup that made one fold take 6.5+ hours. Both fixed without touching any pre-registered parameter, which is the property that makes the GATE FAIL above trustworthy — the result is a measurement, not an artifact of the harness being too slow or too memory-starved to run the real sweep honestly.

**This is the fifth independent confirmation that same-day round trips have no exploitable signal in this codebase** (v1, Run 1, Run 2, Run 3, Run 4's h=1 daily-bar finding, now this dedicated minute-bar track) — the most direct one, since it used real intraday features and a real MIS cost model rather than daily OHLCV standing in for same-day behavior. The `intraday_bars` spine is **kept**, not deleted: it carries no cross-sectional alpha, but remains the right data for *execution* — realistic entry-timing on signals from a horizon that does have edge (see below), via the already-built `execution/fill_model.py`.

`research/intraday_sweep.py` and `evaluation/intraday_backtest.py` stay committed as the reproducible record of a completed, disclosed, negative result — the same convention `phase0_sweep.py` and `phase0_stress.py` follow for Phase 0's own superseded runs. `EXPOSURE_INR = 75,000` inside that retired sweep script is not a live system default; it never reaches the training path, the gate, or the prediction ledger, and is the only capital figure anywhere in the codebase.

## Phase G: the daily brief, on the horizon that actually has edge (in progress, started 2026-08-22)

Per `phase0_verdict.md` Run 4, the one configuration to have passed the pre-registered gate is h=10/top_n=10 (+0.447% net alpha/rebalance, 43 folds, p=0.000085) — trained, so far, only on the 98-symbol `PHASE0_UNIVERSE` of currently-liquid large caps, not the point-in-time mid/small-cap universe `universe_pit.py` already makes available (1,903 tradeable names today, 733 as of 2015, built from the 8.17M-row `bhavcopy_eq` spine). `predictions` currently holds 0 rows — every number to date is a backtest, with no forward track record. **Design invariant carried through every step:** no capital figure is a system parameter. The model, gate, and ledger operate in relative returns and weights only; `optimizer/sizing.py` measures (not assumes) that equity_delivery costs are exactly ticket-size-invariant, so the only capital question that actually applies is whole-share divisibility, not a break-even ticket size.

**G1 (the decisive experiment) is done, and it found a real bug before trusting the result.** The first real run of `research/bhavcopy_rerun_sweep.py` passed all 16 (cap_band × horizon × top_n) combinations at 10-25x Run 4's own alpha magnitude — the same "too good" shape that flagged Run 2's ADANIENT bug. Checked before trusting it: the wider bhavcopy universe contains long-halted symbols whose reopening print gets treated as an ordinary adjacent-day return by `features/engine.py`/`labels/forward_return.py`'s bar-sequence `pct_change`/`shift` calls, fabricating alpha nothing could have captured (1,087 rows with >50% "1-day" moves, median 225 calendar days since the prior print, max 6,011 days — none of it caught by the existing ADANIENT-class adjustment-anomaly quarantine, since raw `close` jumps too, not just the adjustment factor). Fixed with `data/liquidity.py`'s `segment_symbols_by_trading_gap` — splits each symbol's history at gap boundaries so bar-sequence returns reset at a halt exactly like they already reset at a new listing, keeping real history on both sides rather than the far more aggressive whole-symbol quarantine (measured: would have dropped 66% of all rows). Verified a genuine no-op on the 98-symbol Phase 0 path — Run 4's numbers stay reproducible.

**The corrected result (`research/verdict_bhavcopy_rerun.md`): 12 of 16 combinations PASS, and the failure pattern is the finding.** `full_pit`, `mid`, and `small` cap bands pass every (horizon, top_n) combination at magnitudes matching Run 4's own order of magnitude (+0.4% to +2.2%/rebalance). Every **`large`**-cap-band combination **FAILS** — not on magnitude, on significance (hit rate 48-69%, statistically indistinguishable from chance). On a real, survivorship-corrected, point-in-time universe, this pipeline's edge is concentrated in mid/small caps, not large caps — exactly the segment the user's own product requirement asked for, and which no prior run (Run 1-4, all on the 98-symbol large-cap-only `PHASE0_UNIVERSE`) had ever actually tested. This is evidence for the mid/small-cap request, not a guess made in its favor.

**Also built:** `data/loader.py` (the shared `load_candles`/`load_features_and_labels` path, so cli/main.py, the reconcile loop, and research scripts can never silently diverge in which universe they use); `evaluation/gate.py`'s `evaluate_forward_record`/`apply_forward_record_decision` (closes the gap this file's own "Reconcile loop" entry named — a live model's graded forward ledger can now demote it back to shadow on a significantly-underperforming record, reusing the same one-sided binomial test the promotion gate uses); `models/ranker.py`'s `QuantileRanker` (p10/p50/p90 expected-move bands, populating `predictions.predicted_return`/`confidence`, written NULL by every caller until now); `evaluation/calibration.py` (reliability curves/coverage checks on the graded ledger).

**G4 (weekly retrain, 2026-08-22, same day):** `models/train_candidate.py`'s `train_candidate_core` — `cli/main.py`'s `train_candidate` command body, factored out (the same extraction G2 did for the reconcile loop) so `harness/retrain.py`'s `build_weekly_retrain_graph` can call it as a plain function. Idempotency-keyed by ISO week, not calendar date — running it twice in the same week is a no-op after the first success. New CLI: `stocksense retrain-weekly`. Gate criteria remain unreachable from any parameter, exactly as before the extraction.

**G5 (the daily brief, 2026-08-22, same day):** `GET /api/brief` — today's top-N picks from the live model's latest predictions (weighted via the same `portfolio.construct.target_weights_top_n` `predict` already uses), expected-move bands where a `QuantileRanker`-backed model has populated them, yesterday's graded revision, and a capital-agnostic sizing note (`optimizer/sizing.py`'s `min_capital_for_full_positions`, not an assumed account size). A new desktop BRIEF tab (`desktop/renderer/panels/brief.js`) renders it — the one capital input on that page is deliberately client-side only, scaling already-returned weights into an indicative rupee figure in the browser, never sent to the server (verified directly: `test_brief_never_accepts_or_returns_a_capital_field`). Per this file's own standing limitation (`ELECTRON_RUN_AS_NODE=1` in this environment), the rendered window itself could not be visually verified here — `cd desktop && npm start` in a normal interactive session is still needed for that, same as every other desktop-app phase.

## The two contradictions that matter most

**1. Daily cadence → monthly cadence.** The docs (`04`, `05`, `06`) are written around a nightly retrain / daily-horizon prediction cycle. Phase 0 measured this directly: a 1-day holding horizon cannot clear realistic transaction costs, confirmed independently four times (v1's own historical output, and three re-runs in this codebase on different data). The horizon that survives costs is **~20 trading bars (roughly monthly)**. Every daily-cadence detail in `04`–`08` should be read as *the wrong cadence*, not an implementation detail to fill in later.

**2. The three-layer LLM brain → unbuilt, unproven, and possibly unjustified.** `04-model-brain.md` centers on LightGBM → Ollama investigation → Claude synthesis, with an explicit ablation (Baseline 8: LightGBM alone) specified as the test for whether the LLM layers earn their cost. **That ablation has never been run**, because the LLM layers don't exist yet. What's built is Baseline 8 itself — a LightGBM-only cross-sectional ranker — with nothing to compare it against. The docs describe the LLM layers as the differentiator; the only thing proven to work so far is the layer the docs treat as a baseline.

## What "not built" means for anyone picking this up

If you are extending this codebase: **do not assume any document above describes working code.** Check `src/stocksense/` directly, and cross-reference `research/phase0_verdict.md` for what the evidence actually supports before trusting a documented design decision — several were made before evidence existed to test them, and at least two (daily cadence, LLM-centrality) are now known to be wrong or unproven respectively.

The documents are not being deleted or rewritten wholesale, because the reasoning in them — the dual-track invariant, the adversarial-evaluator philosophy, the gate-not-average principle, the point-in-time discipline — is sound and still the target. They describe *intent*, validated in places and contradicted in others. Treat them accordingly.
